Software Quality Control

Exam prep for ISTQB Chapter 1: sections 1.1 to 1.3, plus QC vs QA

Explanation

1. What is software testing?
Definition: Software testing is an activity that checks whether the actual results match the expected results. It helps discover defects and reduce uncertainty about software quality.

Testing is the process of identifying the accuracy and quality of a software product or service. It exists to validate that the product fulfills the prerequisites, needs and desires of the client.

Analogy: a taster at a restaurant compares what the kitchen served (actual) with what the menu promised (expected). Any mismatch is reported.

Objectives of testing (from the slides):

  • Uncover as many errors (bugs) as possible in a given product.
  • Demonstrate that the product matches its requirement specifications.
  • Validate quality using the minimum cost and effort.
  • Generate high-quality test cases, perform effective tests, and issue correct and helpful problem reports.
2. Quality Control (QC) vs Quality Assurance (QA)
QA is the process used to create the deliverables; it is managing for quality. It can be done by a manager, client, or third-party reviewer. Examples: process checklists, project audits, methodology and standards development.
QC covers quality-related activities associated with the creation of deliverables. It verifies the quality of the output: that deliverables are acceptable, complete and correct. Examples: inspection, deliverable peer reviews, and the testing process.

Both are an integral part of the organization’s quality management plan. Testing should be integrated as one of the QA activities.

Analogy: in a car factory, QA designs and audits the assembly-line process; QC inspects each finished car before it leaves.

3. 1.1 Why is testing necessary?

Software systems context. Most people have used software that did not work as expected. Faulty software can cause loss of money, time or business reputation, and could even cause injury or death.

Causes of software defects. A human makes an error (mistake), which produces a defect (fault, bug) in code or a document. If that defect is executed, the system may fail to do what it should: a failure.

Error → Defect → Failure. The person errs, the artifact holds the defect, the running system shows the failure.

Defects occur because humans are fallible and because of: time pressure, complex code, complexity of infrastructure, changing technologies, many system interactions.

Note: failures can also be caused by environmental conditions such as radiation and magnetism. These are failures without a human error in the code.

Testing and quality.

  • Testing lets us measure quality for both functional and non-functional requirements.
  • Finding few or no defects gives confidence in quality.
  • When defects are found and fixed, quality increases.
  • Learn lessons from previous projects: find the root cause of defects, improve processes, prevent recurrence.

How much testing is enough? It depends on the level of risk (technical, safety, business) and project constraints (time, budget). Testing must give stakeholders enough information to decide on release.

4. 1.2 What is testing? (it is more than running tests)

A common belief is that testing only means executing the software. That is part of it, not all. Testing activities exist before and after execution:

  • Planning and control
  • Choosing test conditions
  • Designing and executing test cases
  • Checking results
  • Evaluating exit criteria
  • Reporting on the testing process and the system under test
  • Finalizing or completing closure activities after a test phase
  • Reviewing documents (including source code) and conducting static analysis

Dynamic vs static testing: both can reach similar objectives and provide information to improve the system and the development and testing processes.

Objectives of testing: finding defects, gaining confidence about quality, providing information for decision-making, preventing defects.

Preventing defects: designing tests early (verifying the test basis via test design) helps prevent defects entering code. Reviewing requirements and resolving issues also prevents defects.

Sometimes the main objective is only to assess quality (with no intention of fixing defects), to tell stakeholders the risk of releasing at a given time.

Debugging vs testing. Dynamic testing shows failures caused by defects. Debugging is the development activity that finds, analyzes and removes the cause of the failure. Re-testing by a tester confirms the fix resolves the failure. Testers test; developers debug.
5. 1.3 The seven testing principles

Suggested over the past 40 years; general guidelines common to all testing.

1. Testing shows the presence of defects, not their absence. Testing reduces the probability of undiscovered defects, but finding none is not proof of correctness.

2. Exhaustive testing is impossible. Testing all input and precondition combinations is not feasible except for trivial cases. Use risk analysis, test techniques and priorities to focus effort.

3. Early testing saves time and money. Start static and dynamic activities as early as possible in the lifecycle. Also called shift left. It reduces or eliminates costly changes.

4. Defects cluster together. A small number of modules usually holds most pre-release defects or causes most operational failures. Predicted and observed clusters feed risk analysis to focus testing.

5. Beware of the pesticide paradox. Repeating the same tests eventually finds no new defects, like pesticide losing effect on insects. Change existing tests and data, and write new tests. In automated regression testing the effect is beneficial: a low number of regression defects.

6. Testing is context dependent. Safety-critical industrial control software is tested differently from an e-commerce mobile app; Agile differs from sequential lifecycles.

7. Absence-of-error fallacy. It is a mistaken belief that finding and fixing many defects ensures success. A system can pass all specified requirements and still be hard to use, not meet users’ needs, or be inferior to competitors. Organizations that expect testers to run all tests and find all defects ignore principles 2 and 1.

Smart summary

  • Testing = compare actual vs expected; finds defects, reduces uncertainty.
    • Goals: find many bugs, match requirements, low cost, good test cases and reports.
  • QA = process, managing for quality (audits, checklists, standards). QC = product, verifying output (inspection, peer review, testing).
  • 1.1 Why test?
    • Bad software costs money, time, reputation, even lives.
    • Error → Defect → Failure; environment (radiation, magnetism) can also cause failure.
    • Causes: time pressure, complex code, complex infrastructure, changing technology, many interactions.
    • How much? Depends on risk + time/budget; give stakeholders release information.
  • 1.2 What is testing?
    • Not only execution: planning, conditions, design, run, check, exit criteria, report, closure, reviews and static analysis.

Common mistakes and traps

“Testing proves software is correct.” False. It shows defects exist; it cannot prove none exist.
“Testing = running the program.” False. Planning, design, reviews, static analysis and reporting are testing too.
“Testers fix bugs.” False. Developers debug; testers re-test.
“Finding and fixing all defects guarantees success.” False. That is the absence-of-error fallacy.
Pesticide paradox is not always bad: in automated regression it gives few regression defects.
Do not mix QA (process) and QC (output).
