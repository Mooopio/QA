Software Quality: Exam Prep

Deep Explanation

1. What is software?

Software is more than code. It has four parts: (1) computer programs (code), (2) procedures, (3) documentation, (4) data necessary for operating the system.

Analogy: a restaurant is not only the chef’s cooking (code). It also needs the recipes and routines (procedures), the menu and manuals (documentation), and the ingredients (data).
2. What is software quality?

Two official definitions (memorize both):

  1. The degree to which a system, component, or process meets specified requirements.
  2. The degree to which a system, component, or process meets customer or user needs or expectations.

Definition 1 is about the written spec; definition 2 is about what the user really wants. Quality is described through several dimensions called quality parameters, split into two groups.

5. Error, Defect, Failure, Bug (recommended terminology)

People say “crashed, broke down, error, defect, bug, problem” loosely. The course asks you to use precise terms:

  • Error: (1) a human action that produces an incorrect result; (2) sections of code that are incorrect due to grammatical, logical or other mistakes by an analyst, programmer or other team member.
  • Defect: (1) software errors that cause incorrect functioning during a specific application; (2) a variance between expected and actual. Per the slides, a defect is an error found after the application goes into production.
  • Failure: inability of a system or component to perform its required functions within specified performance requirements. When a defect reaches the end customer it is a failure. During development, failures are usually observed by testers.
  • Bug: the result of a coding error; an error found in the development environment before shipping.
Chain: human makes an Error → it sits in the software as a Defect → when it shows up to the user it is a Failure. Errors can occur in any life-cycle phase. Defects must be found and fixed before they become failures. The causes of all three must be identified.

Sentence matching from the slides: “System crashed during production” = failure; “designer made an error” = error; “review found a defect in the test plan” = defect; “found a bug in a program today” = bug; “client complained about a calculation in the payment report” = problem/failure; “failure reported in the monitoring subsystem” = failure.

6. Case studies

Case 1: Pharmacy cash register. Requirement: block sales over $75 to customers owing over $200. The programmer misunderstood the spec and coded a limit of $500. This is a defect that never caused a failure, because the pharmacy credit card limit was $400, so nobody could ever buy over $500.
Lesson: a defect can exist silently; it only becomes a failure when conditions trigger it.

Case 2: American Signature (furniture). Rule: a customer whose monthly purchase is higher than the average monthly purchases of all customers is a Preferred Customer and gets a gift or major discount once a month. Defect: the algorithm used only the average of current purchases and ignored the customer’s monthly history (poor understanding of the algorithm). Result: a failure; too many Preferred Clients were identified, causing a financial loss.
Lesson: a defect that reaches production becomes a failure with business cost.

7. The 9 causes of software errors
  1. Faulty definition of requirements: erroneous, absent important, incomplete, or unnecessary requirements included.
  2. Client-developer communication failures: misunderstanding client requirements (written, oral) or client responses to design problems.
  3. Intentional deviations from requirements: reusing components from previous projects without full analysis; functionality omitted due to budget or time; “improvements” not in the requirements.
  4. Logical design errors: misinterpreting requirements into design (boundary conditions, algorithms, reactions to illegal operations).
  5. Coding errors: misreading the design document, incorrect use of language constructs.
  6. Non-compliance with documentation and coding instructions: teammates coordinating with non-complying code; people trying to understand, maintain or test it.
  7. Shortcomings of the testing process: incomplete test plan; not reporting all errors; incorrect reporting; incomplete correction of detected errors.
  8. Procedural errors: incorrect procedures for user activities in the software.
  9. Documentation errors: errors in design documents or code comments, and in user manuals.

Smart Summary

  • Software = code + procedures + documentation + data
  • Quality = meets specified requirements AND meets user needs/expectations
  • Technical (objective): Correctness (defect rate), Reliability (failures/hour), Capability (% requirements covered), Maintainability (change logs, impact analysis), Performance (CPU seconds, MB)
  • User (subjective): Usability, Installability, Documentation, Availability, all by satisfaction %
  • Error = human action/incorrect code → Defect = expected vs actual variance (after production) → Failure = defect reaches customer
  • Bug = coding error found before shipping
  • Errors can occur in any phase; fix defects before they become failures; find the causes
  • Case 1: $75/$200 rule coded as $500 → defect, no failure (card limit $400)
  • Case 2: “Preferred Customer” ignored monthly history → failure, financial loss
  • 9 causes: requirements, communication, deviations, logical design, coding, non-compliance, testing shortcomings, procedural, documentation

Common traps

• Don’t say “bug” for something found in production (that’s a defect/failure).
• Reliability = failures per hour; Correctness = bugs per line of code. Do not swap.
• Capability = % of required operations implemented, not speed or size.
• Case 1 had no failure; Case 2 did.
• Software is NOT only code.
• Install-ability and Availability are user parameters, not technical.
