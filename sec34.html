Ch 2 1 · Software development lifecycle models 2.1

A software development lifecycle model describes the types of activity performed at each stage in a software development project, and how the activities relate to one another logically and chronologically.

It is an important part of a tester's role to be familiar with the common SDLC models so that appropriate test activities can take place. In any SDLC model, characteristics of good testing are:

  1. For every development activity, there is a corresponding test activity.
  2. Each test level has test objectives specific to that level.
  3. Test analysis and design for a given test level begin during the corresponding development activity.
  4. Testers participate in discussions to define and refine requirements and design, and are involved in reviewing work products (requirements, design, user stories…) as soon as drafts are available.

The syllabus categorizes models as: Sequential development models and Iterative and incremental development models.

SDLC model = خطة الرحلة: إيه الأنشطة في كل مرحلة وترتيبها. المهم للـ tester: الاختبار مش بيستنى الكود. من أول ما الـ requirements تتكتب كمسودة، الـ tester بيشارك ويراجع (ده ربط مباشر بالـ static testing في Ch 3).

Sequential models: Waterfall and V-model

A sequential development model describes the process as a linear, sequential flow of activities. Any phase should begin when the previous phase is complete. In theory there is no overlap of phases, but in practice it is beneficial to have early feedback from the following phase.

Waterfall: development proceeds through successive phases. Reviews and test preparation can begin early, while dynamic testing requires executable software.

V-model: explicitly links development activities with corresponding test levels. Test analysis and design begin alongside the related development activities. It includes test levels for each development phase, which further supports early testing.

Sequential models deliver software with the complete set of features, but typically require months or years for delivery to stakeholders and users.

Waterfall = سلم نازل: متنزلش درجة غير لما تخلّص اللي فوقها. V-model = نفس السلم، بس كل درجة نزول (تطوير) ليها درجة طلوع قصادها (اختبار): requirements ↔ acceptance، design ↔ system، وهكذا. الشكل حرف V وكل جنب بيقابل التاني.

نقطة مهمة: في Waterfall الـ dynamic testing محتاج software شغّال، لكن الـ reviews وتحضير الاختبار ممكن يبدأوا بدري.

Iterative and incremental models

  • Incremental development: establishing requirements, designing, building and testing a system in pieces, so the software’s features grow incrementally. Increment sizes vary: some methods have larger pieces, some smaller.
  • Iterative development: groups of features are specified, designed, built and tested together in a series of cycles, often of a fixed duration. Iterations may change features from earlier iterations, and project scope.
  • Iterative refines a solution through repeated cycles. Incremental adds capabilities in successive increments. A project may combine both.

Incremental = تبني بيت أوضة أوضة: كل مرة بتضيف حتة جديدة. Iterative = ترسم لوحة وبتعدّل فيها كل دورة لحد ما تتحسن. وممكن تعمل الاتنين: تضيف أوضة جديدة ومعاها تعدّل في اللي اتبنى.

SequentialIncrementalIterative
IdeaLinear flow; next phase starts after previous completesBuild/test system in pieces; features growSeries of cycles refining the solution
DeliveryComplete feature set, months or yearsSuccessive incrementsFixed-duration cycles; may change earlier features and scope
ExamplesWaterfall, V-model(pieces added)(repeated refinement)

Waterfall = water flows one way. V-model = Verify each side. Incremental = “add”. Iterative = “re-do/refine”. Four good-testing rules: C-O-B-P = Corresponding activity, Objectives per level, Begin early (test analysis/design), Participate in reviews.

“No overlap of phases” is true in theory for sequential models; in practice early feedback from the next phase is beneficial. And do not say Waterfall can’t start any testing until the end: reviews and test preparation can begin early, only dynamic testing needs executable software.

Ch 2 2 · Test levels: the big picture 2.2
  • Test levels are groups of test activities that are organized and managed together.
  • Each test level is an instance of the test process.
  • Test levels are related to other activities within the SDLC.

Levels in the syllabus: Component · Component Integration · System · System Integration · Acceptance.

Each level is characterized by: (1) specific objectives (reducing risk, finding defects, verifying specified behaviour, building confidence in the test object’s quality), (2) test basis, (3) test object, (4) typical defects and failures, (5) specific approaches and responsibilities.

Environment: every level needs a suitable test environment. In acceptance testing, a production-like environment is ideal; in component testing, developers typically use their own development environment.

تصنيع عربية: Component = تختبر البوجي لوحده. Component integration = الموتور مع ناقل الحركة (التفاعل بينهم). System = العربية كلها على الطريق. System integration = العربية مع الأنظمة الخارجية (محطة الشحن/السيستم بتاع الدفع). Acceptance = العميل بيجرّبها قبل ما يستلم. كل مرحلة أكبر من اللي قبلها.

LevelFocusTypical responsibility
1 Component (unit)Components in isolationDeveloper who wrote the code
2 Component integrationInterfaces and interactions between componentsOften developers
3 SystemOverall behavior of the entire system, end to end, functional + non-functionalMay be an independent test team
4 System integrationInterfaces to other systems and external servicesGenerally testers
5 AcceptanceValidation and readiness for deployment; meets users’ business needsCustomers, business users, product owners, operators

C-CI-S-SI-A → “Cats Can’t Ignore Silly Sounds, Instantly Alarmed”. The attribute list O-B-O-D-A = Objectives, Basis, Object, Defects, Approaches/responsibilities.

Ch 2 3 · Component (unit) testing Level 1

Component testing (also known as unit testing) focuses on testing components in isolation. It often requires specific support, such as test harnesses or unit test frameworks.

Test basis
  • Detailed design
  • Code
  • Data model
  • Component specifications
Test objects
  • Components, units or modules
  • Code and data structures
  • Classes
  • Database modules
Typical defects and failures
  • Incorrect functionality (not as described in design specifications)
  • Data flow problems
  • Incorrect code and logic
Approach / responsibility

Usually performed by the developer who wrote the code.

الـ isolation هو الكلمة المفتاح: بتعزل الـ component عن باقي السيستم (وبتستخدم test harness أو unit test framework بدل الأجزاء التانية). عشان كده الـ developer نفسه هو اللي بيعمله في الغالب، وبيستخدم بيئة التطوير بتاعته.

Ch 2 4 · Component integration testing Level 2

Component integration testing (also known as unit integration testing) focuses on testing the interfaces and interactions between components. It is heavily dependent on the integration strategy: bottom-up, top-down or big-bang.

Test basis
  • Software and system design
  • Sequence diagrams
  • Interface and communication protocol specifications
  • Use cases
  • Architecture at component or system level
Test objects
  • Subsystems
  • Databases
  • Infrastructure
  • Interfaces
  • APIs
  • Microservices
Approach / responsibility

Often the responsibility of developers.

هنا مش بتسأل “كل component شغال لوحده؟” (ده الـ component testing) لكن “لما يتكلموا مع بعض بيتفاهموا؟”. الـ integration strategies: bottom-up (من تحت لفوق)، top-down (من فوق لتحت)، big-bang (توصّل كل حاجة مرة واحدة).

Component integration = interfaces between components inside the system. System integration (below) = interfaces to other systems and external services.

Ch 2 5 · System testing Level 3

System testing focuses on the overall behavior and capabilities of an entire system or product, often including functional testing of end-to-end tasks and the non-functional testing of quality characteristics. For some non-functional characteristics (e.g., usability) it is preferable to test on a complete system in a representative test environment. Using simulations of subsystems is also possible.

Test basis
  • System and software requirement specifications (functional and non-functional)
  • Risk analysis reports
  • Use cases
  • Epics and user stories
  • Models of system behavior
  • State diagrams
  • System and user manuals
Test objects
  • Applications
  • Hardware/software systems
  • Operating systems
  • System under test (SUT)
  • System configuration and configuration data
Typical defects and failures
  • Incorrect calculations
  • Incorrect or unexpected functional or non-functional behavior
  • Incorrect control and/or data flows within the system
  • Failure to properly and completely carry out end-to-end functional tasks
  • Failure to work properly in the production environment(s)
  • Failure to work as described in system and user manuals
Approach / responsibility

Focus on the overall, end-to-end behavior as a whole, functional and non-functional. May be performed by an independent test team, and is related to specifications for the system.

الـ system testing بيبص للسيستم كصندوق واحد من أوله لآخره (end-to-end)، ومش بس “بيعمل إيه” لكن كمان “بيعمل بجودة إيه” (non-functional). الاختبار على بيئة تشبه الحقيقية، وممكن تستخدم simulations لأجزاء مش متاحة.

Ch 2 6 · System integration testing Level 4

System integration testing focuses on testing the interfaces of the system under test and other systems and external services. Example: check registration with the external payment system.

Typical defects and failures
  • Inconsistent message structures between systems
  • Incorrect data, missing data, or incorrect data encoding
  • Interface mismatch
  • Failures in communication between systems
  • Unhandled or improperly handled communication failures between systems
Approach / responsibility

Needs suitable test environments, preferably similar to the operational environment. Generally the responsibility of testers.

المثال اللي في السلايد: التسجيل (registration) بيكلّم سيستم دفع خارجي. مش بتختبر السيستم بتاعك لوحده، بتختبر الوصلة بينه وبين برّه. العيوب النموذجية كلها عن الرسايل والداتا والـ interfaces.

Ch 2 7 · Acceptance testing Level 5

Acceptance testing focuses on validation and on demonstrating readiness for deployment, which means the system fulfills the user’s business needs. Main forms: UAT · operational acceptance testing (OAT) · contractual & regulatory acceptance testing · alpha & beta testing.

Often the responsibility of customers, business users, product owners or operators; other stakeholders may be involved. Ideally performed by the intended users.

UAT = الزبون بيجرّب العربية ويشوف تناسبه. OAT = ورشة الصيانة بتتأكد إنها تقدر تشغّلها وتعمل backup وتصلّحها. Contractual = بتطابق بنود العقد. Regulatory = بتطابق القانون. Alpha = العملاء بيجرّبوا عندنا في الشركة. Beta = العملاء بيجرّبوا عندهم في بيوتهم.

Forms: U-O-C-R-A-B → “Uncle Omar Cooks Rice And Beans”. Alpha = At Author’s site. Beta = Buyer’s Base.

Alpha is not performed by the development team: it is at the developer’s site, but by customers/operators or an independent team. Beta does not require alpha first. Alpha/beta are for COTS; contractual is for custom-developed software. Acceptance is about validation.

Ch 2 8 · Test types: functional, non-functional, black-box, white-box 2.3

A test type is a group of test activities aimed at testing specific characteristics of a software system, or a part of it, based on specific test objectives. All the mentioned test types can be applied to all test levels, although the focus differs at each level.

Functional testing

Evaluates the functions the system should perform: “what” the system should do. Requirements may be in business requirements specifications, epics, user stories, use cases, functional specifications, or undocumented. Performed at all levels (e.g., component tests based on a component specification). Considers behavior, so black-box techniques may be used.

Non-functional testing

Evaluates characteristics such as: Performance efficiency · Compatibility · Usability (interaction capability) · Reliability · Security · Maintainability · Portability (flexibility) · Safety. It tests “how well” the system behaves. Can and often should be done at all levels, as early as possible. Black-box techniques may be used.

الآلة الحاسبة: Functional = بتجمع 2+2 صح؟ (إيه بتعمل). Non-functional = بتجمع بسرعة؟ آمنة؟ سهلة؟ بتشتغل على كل الأجهزة؟ (قد إيه كويس بتعمل).

Black-box testing is specification-based: derives tests from documentation not related to the internal structure of the test object. Main objective: checking the system’s behavior against its specifications.

White-box testing is structure-based: derives tests from the system’s implementation or internal structure (code, architecture, work flows, data flows). Main objective: to cover the underlying structure by the tests to an acceptable level.

Black-box = صندوق مقفول: بتجرّب من بره وبتقارن بالـ specification. White-box = صندوق شفاف: شايف الكود والـ flows، وهدفك تغطي الـ structure.

The 8 non-functional: P-C-U-R-S-M-P-S → “Please Check Users’ Real Safety, Maintenance, Portability, Security”. (Performance, Compatibility, Usability, Reliability, Security, Maintainability, Portability, Safety.) Functional = WHAT. Non-functional = HOW WELL.

Ch 2 9 · Confirmation and regression testing 2.3

Changes are made to a component or system either to enhance it (new feature) or to fix it (remove a defect). Testing should then include confirmation testing and regression testing, needed on all test levels if defects are fixed and/or changes are made at that level.

Confirms that an original defect has been successfully fixed. Depending on risk: (1) execute all tests that previously failed due to the defect, or (2) add new tests to cover changes needed to fix the defect. If time or money is short, it might be restricted to exercising the test steps that should reproduce the failure and checking that the failure does not occur.

Confirms that no adverse consequences have been caused by a change, including a fix that has already been confirmation tested. They could affect the same component, other components in the same system, or other connected systems. It may also relate to the environment. It is advisable first to perform an impact analysis to recognize the extent of regression testing; impact analysis shows which parts of the software could be affected.

سبّاك صلّح صنبور بيسرّب. Confirmation = تفتح الصنبور وتتأكد إن التسريب نفسه اتصلّح. Regression = تتأكد إن التصليح ما كسرش المواسير التانية أو ضغط المية في الشقة كلها. وقبلها بتعمل impact analysis: إيه الأجزاء اللي ممكن تتأثر.

ConfirmationRegression
QuestionIs the original defect fixed?Did the change break anything else?
ScopeThe defect and its failing testsSame component, other components, other systems, environment
HelperRe-run previously failed tests / add testsImpact analysis first

The slide lists these for extra reading: Test-driven development (TDD) · Acceptance Test-Driven Development (ATDD) · Behavior-Driven Development (BDD) · DevOps, CI/CD.

Confirmation = “is this fix good?”. Regression = “did the fix hurt other things?”. Regression is not limited to the changed component, and it can also cover the environment.

Ch 3 11 · What is static testing? Basics
  • Examine a work product without executing the software under test.
  • People can review documents, designs, source code, project documentation, contracts, models and test cases.
  • Tools can analyse suitably structured work products.
  • The analysis tool may run while the software being examined does not.

Example: read a registration rule and identify a contradiction before coding.

مراجعة مسودة الامتحان قبل الطباعة: بتقراها وبتلاقي سؤالين متناقضين من غير ما حد يحل الامتحان. ده static. لما الطلبة يحلوا الامتحان فعلاً ده dynamic.

Verification and validation

Verification

Does the work product meet its specified rules?

Example: does the design match the approved 18-credit limit?

Validation

Does the proposed rule meet the users’ actual needs?

Example: do graduating students need an agreed exception?

Verification = “بنبني الحاجة صح حسب القواعد؟” Validation = “القاعدة نفسها صح للمستخدمين؟”. ولاحظ في المثال: التصميم مطابق للـ 18 credit (verified)، بس لسه ممكن الطلبة المتخرجين يحتاجوا استثناء (validation).

Work products we can examine

Work productIllustrative review question
Requirement or user storyIs the permitted credit limit clear and consistent?
Design or interface specificationDo the caller and receiver agree on the student ID format?
Source codeDoes the condition implement the agreed limit?
Test case or test planIs an expected outcome or important risk missing?

Reviews need understandable material. Tools need a structure they can analyse.

Verification = “Value the Rules” (matches specified rules). Validation = “Values the Users” (meets users’ needs).

Ch 3 13 · Worked examples: requirement review and code review Examples

Review a requirement: three kinds of problem

Ambiguity

“The registration page should respond quickly.”

What response time and workload would count as acceptable?

Contradiction

R1: Accept totals up to and including 18 credits.
R2: Reject totals of 18 credits or more.

They disagree at exactly 18.

Missing information

“Send a password-reset link.”

When should the link expire, and can it be reused?

Clarify the intended rules before developers and testers make different assumptions.

Review the code

Agreed requirement: accept a valid registration when the total is at most 18 credits.

bool canRegister(int total) { return total < 18; }

Review finding: the comparison excludes 18. The agreed boundary requires <= 18. Reading the code reveals the defect. Executing with 18 can reveal its failure.

لاحظ الفرق بين المصطلحات: القراءة بتكشف الـ defect (العيب في الكود < 18)، والتنفيذ بـ 18 بيكشف الـ failure (السلوك الغلط). ده نفس error → fault → failure من الشابتر الأول، وكمان نفس نوع boundary error (> مقابل >=).

Ch 3 15 · Why static testing is valuable; early and frequent feedback Benefits
  • Find unclear or conflicting rules before they spread into design, code, and tests.
  • Find problems in work products that cannot be executed.
  • Improve shared understanding between users, analysts, developers, and testers.
  • Reduce avoidable rework while recognising the effort needed for reviews.

Example: resolve the 18-credit contradiction once, before several modules implement it.

Early question

Before coding, a student-services representative explains when advisor approval is required.

Frequent follow-up

After the rule changes, the team reviews the revised examples and acceptance criteria.

Benefit

The team can adjust the intended behaviour before investing in the wrong solution.

تصحيح غلطة في الرسمة الهندسية بياخد دقيقة. تصحيحها بعد ما الحيطان اتبنت بياخد أسابيع. نفس الفكرة: المشكلة اللي اتمسكت بدري ما انتشرتش في design وcode وtests.

P-I-I-C-F → “Plan, Initiate, Individually review, Communicate, Fix and report”. Arabic: “خطّط، ابدأ، راجع لوحدك، ناقش، صلّح وقدّم تقرير”.

Planning and review initiation

  • Objective and scope: review only the credit-limit and prerequisite rules in document version 2.
  • Illustrative exit criteria: resolve every contradiction and give each remaining action an owner.
  • Preparation: invite the relevant reviewers; share the exact version, checklist, roles and review time.

A review needs a clear target and enough preparation time.

Individual review: a small checklist

Clarity

Could two readers interpret the rule differently?

Consistency

Does another rule say something incompatible?

Completeness

Are important cases or conditions missing?

Testability

Can we decide whether the expected result happened?

Traceability

Does the test set cover each agreed acceptance criterion?

Example finding: no test checks acceptance of exactly 18 credits.

C-C-C-T-T = Clarity, Consistency, Completeness, Testability, Traceability. “3 C’s and 2 T’s”.

Anomaly or confirmed defect?

Logged anomaly

“The reset link has no expiry time in this user story.”

Analysis

Is expiry defined in a referenced security specification, or is the requirement incomplete?

Decision and follow-up

Confirm a defect, clarify an existing rule, or close the finding with a recorded reason.

A suspected problem needs analysis before we treat it as a confirmed defect.

Review leader ≠ moderator. Leader = organizes (selects reviewers, schedules). Moderator = facilitates the discussion. Manager provides resources, not the review itself.

Work: A-R-S (Author, Reviewer, Scribe). Organize: M-L-M (Manager, Leader, Moderator): “Manager gives time, Leader picks people, Moderator keeps order”.

Choose formality using the objective, work product, risks, and available resources. All four types can reveal anomalies; their purposes and structure differ.

  • Follow the complete generic review process.
  • Use defined roles, preparation, and review criteria.
  • Collect metrics to improve the work process and the inspection process.
  • The author cannot act as the review leader or scribe.

Review the work product. Avoid using findings to rank or blame individuals.

  • Consider the objective, product complexity, criticality, and risks.
  • Consider the SDLC, process maturity, business domain, and team culture.
  • Check applicable obligations and any need for a traceable audit record.
  • Match the review effort to available people, time, and expertise.
  • A draft may receive an informal review before a more formal review.

Example: a critical eligibility rule needs deeper scrutiny than a minor wording change.

Ch 3 19 · Successful reviews and the practice exercise Success + practice
  • Set clear objectives and measurable exit criteria.
  • Choose an appropriate review type and examine manageable pieces.
  • Provide training, preparation time, and management support.
  • Facilitate respectful discussion about evidence.
  • Make reviews part of a culture of learning and improvement.
  • Give feedback to authors and stakeholders, then track corrections.

Example comment: “R1 and R2 disagree at 18 credits. Which outcome is intended?”

Practice exercise

Requirement

“A student may register for up to 18 credits.”

Test case draft

Input: total = 18 credits.
Expected result: reject registration.

Discuss: what is inconsistent? Is reading this test case static or dynamic? Who creates the work product, and who could review it? (Assume the requirement is approved and all other eligibility checks pass.)

  • “Up to 18” includes 18, so expecting rejection conflicts with the approved rule.
  • Reading and comparing the requirement and test case is static testing.
  • Executing that case against the application would be dynamic testing.
  • The test-case writer is its author. Another tester, developer, or business expert could review it.

A review can reveal a defect in the test before it creates a misleading failure report.

  • Static testing examines work products without executing the software under test.
  • Use reviews and static analysis alongside dynamic testing.
  • Analyse anomalies, agree actions, and check that corrections resolve the findings.
  • Choose review roles and formality to fit the purpose and risk.

Simple idea: examine early, discuss clearly, and follow up.

Ch 2 SDLC models 2.1
  • SDLC model = activities at each stage + how they relate logically and chronologically
  • 4 rules of good testing (any model): corresponding test activity for each dev activity · level-specific objectives · test analysis/design begin during the corresponding dev activity · testers join requirement/design discussions and review drafts early
  • Sequential: linear; next phase starts after the previous completes (theory: no overlap)
    • Waterfall: reviews and test preparation can start early; dynamic testing needs executable software
    • V-model: links each development activity to a test level; supports early testing
    • Delivers complete features but takes months or years
  • Incremental: build/test in pieces, features grow · Iterative: cycles (often fixed length) that refine, may change earlier features and scope · may be combined

Ch 2 Test types 2.3
  • Test type: group of test activities for specific characteristics; applies to all test levels (focus differs)
  • Functional = “what” the system does (requirements may be undocumented); black-box techniques
  • Non-functional = “how well”: performance efficiency, compatibility, usability (interaction capability), reliability, security, maintainability, portability (flexibility), safety; at all levels, as early as possible
  • Black-box = specification-based (check behavior vs specs) · White-box = structure-based (cover the underlying structure)
  • Confirmation: original defect fixed? (re-run failed tests / add tests; minimal: reproduce steps) · Regression: no adverse consequences from a change (same component, other components, other systems, environment); do impact analysis first
  • Extra reading: TDD, ATDD, BDD, DevOps, CI/CD
Ch 3 Static testing basics Core
  • Static testing = examine a work product without executing the software under test; people (reviews) and tools (static analysis)
  • Work products: documents, designs, source code, project documentation, contracts, models, test cases

Common mistakes and traps Marks lost here
  • “Regression” is a test type, not one of the 5 test levels.
  • Waterfall: only dynamic testing must wait for executable software; reviews and test preparation start early.
  • Component integration ≠ system integration (internal components vs external systems/services).
  • Alpha is at the developer’s site but not by the dev team; beta may occur without alpha.
  • Business rules not implemented correctly appears as an acceptance defect; inconsistent message structures as system integration; data flow problems as component.
  • Test types apply to all levels; non-functional testing should start as early as possible.
  • Regression is not limited to the changed component, and impact analysis comes first.
  • Static testing never executes the software under test, but static analysis tools do run.
  • Static does not replace dynamic testing: it cannot measure response time.
  • Verification = specified rules; validation = users’ actual needs. Don’t swap them.
  • An anomaly is not automatically a defect: analyse it first.
  • Review leader organizes; moderator facilitates.
  • Inspection: author cannot be review leader or scribe. Walkthrough: author leads, prep optional.
  • Don’t use review findings to rank or blame individuals.
